• Web Worker に処理を逃がす: エクスポートボタンを押したら、データと .meta.jsonc を Web Worker に渡してバックグラウンドで生成し、完了したらダウンロードさせる構成にすると、10万行でもUIが一切固まりません。

10万行でこれで動くなら１００万行でも大丈夫なのかな

基本的には100万行でも動きますが、「単純に10倍の時間がかかるだけ」ではなく、メモリ容量やブラウザ（Webview）特有の「壁」にぶつかるラインになります。
10万行で 116 ms（約0.1秒）という驚異的なスピードが出ているため、描画の仕組み（仮想スクロール）自体は100万行でもそのまま通用します。ただし、100万行（1000万セル）になると「描画以外のボトルネック」が顔を出してきます。

100万行にしたときにぶつかる「3つの壁」と対策


ボトルネック	100万行で起きること	突破するための対策
1. メモリ消費（約1GB〜2GB増）	JavaScriptの配列に100万行×10列の文字列オブジェクトをそのまま展開すると、V8エンジンのメモリ消費が一気に跳ね上がります。	・セルのデータをオブジェクト配列ではなく2次元のプリミティブ文字列配列（または列ごとの配列＝カラムナ形式）で保持する。
・Undo履歴は「全データのコピー」ではなく「変更したセルの差分（座標と旧値）」だけを記録する。
2. スクロールバーの高さ上限	ブラウザのCSSには height の上限（Chrome系で約1,677万px〜3,355万px付近）があり、1行 28px × 100万行 ＝ 2,800万px だと一番下までスクロールできなくなる現象が起きます。	・行の高さを少し詰める（24px なら2,400万pxで収まる）、または仮想スクロールの計算で「スクロール位置の比率（0〜100%）」を自前でマッピングする方式にする。
3. 初期パースと通信（VS Code ↔ Webview）	VS Code側でテキストを丸ごと読み込み、JSON文字列化して Webview に postMessage で送ると、シリアライズだけで数秒フリーズします。	・パース処理を Web Worker に逃がす。
・または、全行を一度に送らず「画面表示に必要な範囲」やバイナリ（ArrayBuffer）で受け渡す。

現在の実装がすでに「10万行で116ms」という無駄のない構造になっているため、100万行のダミーデータを食わせてみれば、おそらく1〜1.5秒程度で普通に開く可能性が高いです。
ただ、もしスクロールが一番下まで届かなかったり、ソートや検索で一瞬固まったりした場合は、上記の「スクロール高さ上限」か「メインスレッドでのソート/検索」が原因です。まずは100万行のテストデータを生成して、そのまま読み込ませてみるのが一番早くて確実ですね！
