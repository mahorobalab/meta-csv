
Web と Windows ネイティブと VS Code プラグインとして動くアプリ作るには何を選ぶといい？

Tauri（Rust + Webフロントエンド）または Electron をベースに、UI部分を TypeScript + React（または Vue / Svelte） で作る構成が最もおすすめです。
この構成なら、UIのコード（HTML/CSS/JS）を1つ書くだけで、Webアプリ・Windowsアプリ・VS Code拡張機能（Webview）の3つすべてでほぼそのまま再利用できます。

1. 具体的なおすすめ技術スタック


レイヤー	選ぶべき技術	理由
言語・UI	TypeScript + React (または Vue / Svelte)	VS Code拡張機能のUI（Webview）もWeb技術で動くため、フロントエンドの資産を3プラットフォームで100%使い回せます。
Windows ネイティブ	Tauri (推奨) または Electron	Tauri は軽量・高速でメモリ消費が少なく、RustでOS固有の処理も書けます。Node.jsの資産をそのまま使いたい場合は Electron が手軽です。
VS Code プラグイン	VS Code Extension API (Webview)	VS Codeのパネルやエディタ内にWeb画面を埋め込む仕組みです。Reactで作った画面をそのまま表示できます。
プロジェクト構成	モノレポ (Turborepo / pnpm workspaces)	packages/ui（共通UI）、apps/web、apps/desktop、apps/vscode のようにディレクトリを分けると管理が圧倒的に楽になります。


2. Tauri と Electron の選び方（Windowsアプリ側）

Windowsネイティブ部分の枠組みは、アプリの性質によって以下のように選ぶのがベストです。
• Tauri を選ぶべきケース（基本はこちら）
	• 起動の速さやメモリの軽さを重視したい。
	• 配布ファイルのサイズを小さくしたい（数MB〜十数MB程度）。
	• ローカルファイルの高速な処理や、OSの深い機能を使いたい。
• Electron を選ぶべきケース
	• Rustを新しく覚える学習コストを避けたい。
	• 既存のNode.jsライブラリ（npmパッケージ）をバックエンド処理で大量に使いたい。
	• VS Code自体がElectron製なので、環境を完全に揃えたい。

3. 開発をスムーズに進めるコツ

1. 通信処理の抽象化（重要）
UIからデータを取得・保存する処理は直接APIやOSを叩かず、インターフェース（Adapterパターン）を挟みます。
	• Web版: fetch でサーバーAPIと通信
	• Windows版: Tauriの invoke（またはElectronのIPC）でローカル処理
	• VS Code版: vscode.postMessage で拡張機能本体と通信
2. UIコンポーネントの統一
VS Code拡張機能では、VS Codeのテーマカラー（ダーク/ライトモード等）に自動で合わせるため、CSS変数（--vscode-editor-background など）が提供されています。共通UI側でこの変数にフォールバックを設定しておくと、VS Code内でも違和感なく馴染みます。

CSV エディタで、メタデータを見て表示とか列幅とか制御できるやつあるといいなとちょっと思いました。決定版がないって聞いたから

メタデータ（別ファイルやスキーマ定義）を読み込んで列幅や表示を制御できるCSVエディタ、確かに「これ！」という決定版が少ないニッチかつ実用的なアイデアですね。開発者の視点でも非常に面白いテーマだと思います。
その用途（高速なテーブル描画、CSVパース、別ファイルのメタデータ連携）に特化する場合、以下の技術構成にするとWeb・Windows・VS Codeの3環境で非常にスムーズに開発できます。

1. CSVエディタ特化のおすすめ技術スタック


役割	おすすめのライブラリ / 技術	選定理由
テーブルUI（心臓部）	TanStack Table + TanStack Virtual	ヘッドレスUIなので自由度が高く、仮想スクロールを組み合わせることで数万行のCSVでもWebview上でサクサク動きます。列幅の動的変更や表示/非表示の制御も標準で得意です。
CSVパース処理	PapaParse (JS) または Rustのcsvクレート	数MB程度ならフロントエンドの PapaParse（Web Worker対応）で十分高速です。3環境でロジックを完全共通化できるメリットが大きいです。
メタデータ定義	JSON Schema または 独自YAML/JSON	data.csv に対して data.csv.meta.json のようなサイドカーファイルを自動探索して読み込む仕様にすると、どの環境でも扱いやすくなります。
Windows ネイティブ	Tauri	Rustは学習コストが少しありますが、UIやCSV処理をTypeScript側に寄せてしまえば、Tauri側は「ファイルの読み書きをするだけ」の薄いラッパーとして使えるため、Rustを深く書く必要はありません。


2. 3環境で「メタデータ連携」をどう実現するか

CSVファイル本体だけでなく「隣のメタデータファイル」も同時に扱う必要があるため、環境ごとのファイルアクセスを以下のように吸収するのがポイントです。
• VS Code 拡張機能
	• CustomTextEditorProvider を使うと、.csv を開いた瞬間に自作のReact画面が立ち上がります。
	• 拡張機能側（Node.js環境）で同じフォルダ内の .meta.json を探し、CSVデータと一緒にWebviewへ渡します。列幅をドラッグで変えたら、即座に .meta.json へ自動保存することも可能です。
• Windows ネイティブ (Tauri)
	• TauriのファイルシステムAPIを使い、CSVを開いた際に同階層のメタデータを自動で読み込みます。
• Web アプリ
	• ブラウザの File System Access API（showOpenFilePicker など）を使うと、Web版でもローカルフォルダへのアクセス許可を得て、CSVとメタデータファイルのペアを読み書きできます。

3. 開発の進め方（おすすめステップ）

いきなり3環境を同時に作ると大変なので、以下の順で進めると手戻りが少なくなります。
1. まずWeb単体（React + TypeScript）でコア機能を作る
	• TanStack Table を使ってCSVの表示・編集・列幅変更・メタデータJSONの適用を完成させます。
2. VS Code 拡張機能に組み込む
	• 作ったReactアプリをビルドし、VS CodeのWebviewに読み込みます（ここが一番需要が高く、テストもしやすいです）。
3. Tauri でラップしてWindowsアプリ化する
	• 同じReactアプリをTauriのフロントエンドとして配置し、ビルドすれば完成です。
この構成で進めるにあたり、よろしければ以下を教えてください。
• メタデータの仕様（既存の標準規格に合わせたいか、列幅や表示/非表示・型定義などの独自JSONから始めたいか）
• 想定するCSVのデータ規模（数千行レベルか、数十万行〜数GBの巨大ファイルも扱いたいか）
これらが分かれば、最適なパース処理や仮想スクロールの設計をさらに具体化できます。
パーソナライズなしで試す

Tauri は、Macアプリもそのまま作れるの？

はい、Tauri は同じソースコードから Mac アプリ（macOS）もそのまま作れます。 Windows、macOS、Linux の3大デスクトップOSすべてに対応しています。
ただし、実際にビルド（配布用のインストーラーや .app ファイルの作成）を行う際には、いくつか重要な仕様と注意点があります。

1. ビルド環境の制約（クロスコンパイル不可）

Tauri は各OSに標準搭載されている WebView（Windows なら Edge WebView2、Mac なら Safari の WKWebView）を利用して動作します。そのため、ビルドは原則としてターゲットとなるOS上で行う必要があります。
• Windows アプリのビルド: Windows マシン上で行う
• Mac アプリのビルド: Mac マシン上で行う

手元に Mac がない場合の解決策

Windows しか持っていない場合でも、GitHub Actions などの CI/CD サービスを使うのが一般的です。GitHub の無料枠でも macOS の仮想マシンが使えるため、コードを push するだけで「Windows用（.exe / .msi）」と「Mac用（.dmg / .app）」の両方を自動でビルドしてリリースページに並べることができます。

2. Mac 向けに開発・配布する際の注意点

コード自体は共通で動きますが、Mac 特有の仕様がいくつかあります。
• 画面表示の微妙な差異（WebViewの違い）
	• Windows は Chromium ベース（Edge）、Mac は WebKit ベース（Safari）で画面を描画します。
	• モダンな CSS や React であればほぼ同じに見えますが、スクロールバーの挙動やフォントの太さ、一部の新しい CSS 機能でわずかに見た目が変わることがあります。
• ショートカットキーの違い（Ctrl と Cmd）
	• CSV エディタで「保存（Ctrl+S / Cmd+S）」や「コピー＆ペースト」を実装する場合、OS に応じて修飾キーを切り替える処理が必要です（Tauri やブラウザの標準イベントで簡単に判定できます）。
• 配布時の署名・公証（Notarization）
	• 個人利用や身内への配布なら問題ありませんが、一般公開して他の人の Mac で警告（「開発元が未確認のため開けません」）を出さずに起動してもらうには、Apple Developer Program（年間99ドル） に登録して署名・公証を行う必要があります。

3. まとめ

• ソースコードは100%使い回せる（ファイルの読み書きAPIなども Tauri が OS の違いを自動で吸収してくれます）。
• ビルドだけは Mac 実機 か GitHub Actions を使う必要がある。
• 将来的に Mac 対応を見据えるなら、最初から Tauri を選んでおけば後からでも簡単に対応できます。

メタデータはJSONでいいのかな？ Yaml は考慮外？ か、あんまり流行ってないもんね

はい、メタデータは JSON で全く問題ありませんし、むしろ今回の CSV エディタには JSON の方が圧倒的に向いています。
YAML を積極的には推さない理由も含め、JSON がベストである技術的な理由は以下の通りです。

1. 今回のアプリで JSON を選ぶべき理由

• GUI（画面操作）からの自動更新が圧倒的に楽
	• CSV エディタ上でユーザーが列幅をドラッグして変えたとき、裏側でメタデータファイルを自動保存（上書き）する処理が必須になります。
	• JSON なら JSON.stringify(data, null, 2) だけで綺麗に整形して書き出せます。一方、YAML はプログラムから上書き保存すると、人間が書いたコメントが消えたり、インデントやクォートのスタイルが崩れたりして非常に扱いにくいです。
• 追加ライブラリ不要で高速
	• TypeScript / JavaScript でも Rust（Tauri）でも、JSON は標準機能だけでパース・書き出しができます。外部ライブラリが不要なため、アプリのサイズも小さく保てます。
• 型チェック・バリデーションとの相性が良い
	• JSON Schema を用意しておけば、ユーザーが VS Code でメタデータファイルを手動編集する際にも、入力補完やエラーチェックが自動で効きます。

2. YAML はどういう場合ならアリ？

もし「人間が手書きでガッツリ設定ファイルを作り込み、コメントをたくさん残したい」という用途がメインなら YAML も選択肢に入ります。ただ、インデントのズレによる構文エラーが起きやすいことなどから、新規のツールやアプリの設定ファイルでは JSON（またはコメントが書ける JSONC、設定ファイル向けの TOML）が選ばれることが増えています。
今回の「GUI操作の結果（列幅や表示状態など）を保存・同期するメタデータ」という性質を考えると、JSON 一択で進めるのが最もシンプルでトラブルが起きません。

3. メタデータ JSON のイメージ

たとえば users.csv に対して users.csv.meta.json のようなファイルを作り、以下のような構造にするのが分かりやすいです。
json
{
  "$schema": "https://example.com",
  "version": "1.0",
  "columns": {
    "id": {
      "width": 80,
      "visible": true,
      "align": "right"
    },
    "name": {
      "width": 200,
      "visible": true,
      "label": "氏名"
    },
    "internal_note": {
      "visible": false
    }
  }
}
コードは注意してご使用ください。
このようにしておけば、列をドラッグして幅を変えた瞬間に width の数値だけを書き換えて保存する処理も数行で書けます。
メタデータの形式が固まってきましたね。次はどの部分を具体化していきましょうか？
• メタデータで制御したい項目（列幅・表示/非表示のほかに、型バリデーション、ドロップダウン選択肢、色分けなど入れたい機能）
• モノレポの具体的な初期構築手順（Web・VS Code・Tauri を動かすためのコマンドとフォルダ構成）
気になる方を選んでいただければ、それに合わせて詳細をお出しします。

JSONCの方が良さそうね。VS Codeはそうだよね

はい、JSONC（JSON with Comments）は非常に良い選択です。VS Code の settings.json や tsconfig.json でも採用されており、開発者にとっては最も馴染み深く、コメントや末尾カンマが許容されるため人間による手書き編集のストレスが大幅に減ります。
メモしておきましたので、今後のメタデータ設計は JSONC を前提に進めましょう。

1. JSONC を採用する際の実装ポイント

標準の JSON.parse() はコメントがあるとエラーになるため、以下のライブラリを使うと安全かつ綺麗に扱えます。
• jsonc-parser（Microsoft公式・推奨）
	• VS Code 本体でも使われている軽量ライブラリです。
	• 最大の強みは、「コメントやフォーマットを壊さずに、特定の値（列幅など）だけを部分的に書き換えて保存する機能（modify / applyEdits）」が標準で備わっている点です。
	• これにより、「人間が書いたコメントを残したまま、GUIでドラッグ変更した列幅の数値だけを更新する」という理想的な挙動が実現できます。

2. メタデータ JSONC のイメージ（users.csv.meta.jsonc）

jsonc
{
  "$schema": "https://example.com",
  "version": "1.0",
  "columns": {
    "id": {
      // システム管理用の連番（編集不可にする想定）
      "width": 80,
      "visible": true,
      "readonly": true,
      "align": "right"
    },
    "status": {
      "width": 120,
      "visible": true,
      "type": "enum",
      "options": ["draft", "published", "archived"] // ドロップダウン候補
    },
    "internal_note": {
      // 普段は隠しておく備考欄
      "visible": false
    }
  }
}
コードは注意してご使用ください。

meta-csv ってドメイン全然空いてるな。誰も考えたこと無いのかな

meta-csv というシンプルで覚えやすいドメインが空いているのは、かなりの狙い目（ブルーオーシャン）です。
実は「CSVにメタデータを持たせる」という考え方自体はデータサイエンスやオープンデータの分野に存在するのですが、「エンジニアや実務者が日常的に使う、軽量なGUIエディタの体験」に落とし込んだ決定版が不在なため、この名前が埋まっていません。
誰も手をつけていない（あるいは決定版が生まれていない）背景には、主に3つの理由があります。

1. なぜ「決定版」が存在しなかったのか？

1. 既存の標準規格が重厚長大すぎた
	• 実は W3C の CSV on the Web (CSVW) や Frictionless Data (Table Schema) といった「CSVにJSONでメタデータを紐づける国際標準」はすでに存在します。
	• しかし、これらは主に政府のオープンデータ公開やデータ分析基盤向けの堅苦しい仕様であり、「列幅を120pxにしたい」「この列は一時的に非表示にしたい」といったエディタとしての使い勝手（UI/UX）を重視した軽量なフォーマットではありません。
2. Excel と テキストエディタ の「隙間」に落ちていた
	• 「列幅や色を変えたいなら Excel（.xlsx）を使えばいい」という派閥と、「Git で差分管理したいからプレーンな CSV でいい（見た目は我慢する）」というエンジニア派閥に分かれていました。
	• 「Git で綺麗に差分管理できるプレーンな CSV のまま、Excel のような快適な見た目・入力補助をサイドカーファイル（JSONC）で実現する」という発想は、まさにその隙間を突くアプローチです。
3. マルチプラットフォーム対応のハードルが高かった
	• 以前なら「VS Code 拡張機能」「Windows アプリ」「Mac アプリ」「Web アプリ」を別々に作る必要があり、個人開発ではコストが見合いませんでした。今は TypeScript + React + Tauri + VS Code Webview があるおかげで、1人で全環境をカバーできるようになっています。

2. ネーミングとしての meta-csv の強さ

• 直感的で分かりやすい: 名前を見ただけで「メタデータ付きの CSV ツール」であることが一発で伝わります。
• 拡張子やスキーマ名にも使える:
	• サイト/アプリ名: MetaCSV (meta-csv.dev や meta-csv.app など)
	• メタデータファイルの命名規則: users.csv.meta.jsonc または users.metacsv.jsonc
	• VS Code 拡張機能ID: meta-csv

普通に作ると１０万行あったらフリーズするよね

はい、普通に <table> や <div> を10万行分すべて描画すると、ブラウザ（WebView）のメモリがパンクして確実にフリーズします。
しかし、正しい設計（3つの鉄則）を取り入れれば、10万行どころか100万行の CSV でも 60fps でヌルヌル動くエディタを Web・VS Code・Tauri の共通コードで作ることができます。

1. 10万行でもフリーズさせない「3つの鉄則」

1. 仮想スクロール（Virtualization）を使う【必須】
	• 画面に見えている範囲（約30〜50行分）の HTML 要素だけを描画し、スクロールに合わせて中身を高速に入れ替える技術です。
	• 10万行あっても DOM 要素は常に数十行分しか存在しないため、描画の重さは「50行のテーブル」と全く変わりません。
	• 採用ライブラリ: TanStack Virtual（または React Virtuoso / Canvasベースの Glide Data Grid）。
2. CSV のパースと検索を別スレッド（Web Worker）に逃がす
	• メインスレッド（画面の操作を受け付ける場所）で10万行の文字列分割やフィルタリングを行うと、処理が終わるまで画面が固まります。
	• Web Worker（裏側の別スレッド）で PapaParse や検索処理を動かせば、読み込み中や検索中でも画面は一切フリーズしません。
3. 巨大データの保持形式を工夫する（オフセットインデックス方式）
	• 10万行×20列をすべて JavaScript のオブジェクト配列 [{ col1: "...", col2: "..." }] に変換すると、メモリを大量に消費し、ガベージコレクション（GC）で一瞬カクつくことがあります。
	• さらに高速化したい場合、CSV全体の文字列（または Uint8Array）は1つだけメモリに持ち、「各行の開始バイト位置の配列（Int32Array）」だけを作って、画面に表示する30行分だけをその場でパースする手法（SmoothCSV や VS Code 本体が採用している手法）を使うと、メモリ消費を劇的に抑えられます。

2. さらに超高速化したい場合の選択肢

• DOM テーブル vs Canvas テーブル
	• DOM ベース（TanStack Table + TanStack Virtual）: CSS で自由自在にデザインでき、セルの編集 UI（ドロップダウンや入力欄）を作りやすいです。10万行程度ならこれで十分サクサク動きます。
	• Canvas ベース（Glide Data Grid など）: 1枚の <canvas> に文字を直接描画するため、数百万行・数千列でも圧倒的な軽さで動きます（Google スプレッドシートと同じ方式）。

3. 環境ごとのちょっとした注意点（VS Code）

Web と Tauri はファイルをストリームやバイナリで直接読み込めますが、VS Code の CustomTextEditorProvider は、ファイル全体を1つの巨大な文字列としてメモリに展開する仕様のため、数十MB（数十万行）を超えると VS Code 自体の制限に引っかかることがあります。
• 解決策: VS Code 側では CustomReadonlyEditorProvider（またはカスタムエディタ）を使い、拡張機能（Node.js）側でファイルをストリーム読み込みして Webview に渡す設計にしておけば、VS Code でも巨大ファイルを安全に開けます。
10万行規模を見据えたアーキテクチャのイメージが固まりましたね。次はどの部分に踏み込みましょうか？
• テーブル描画エンジンの選定（CSSで作りやすい TanStack Virtual か、超巨大データ特化の Glide Data Grid か）
• プロジェクトの初期セットアップ（Web・VS Code・Tauri の3環境が動く最小構成の作成）
進めたい方を教えていただければ、具体的な実装サンプルをお出しします。

Glide Data Grid の方がいいの？

「Excel や Google スプレッドシートのような操作感（範囲選択・コピペ・爆速スクロール）」を最優先するなら Glide Data Grid が圧倒的に有利です。一方で、「メタデータ（JSONC）でセルの見た目や入力UIを柔軟にカスタマイズしたい」なら TanStack Table + TanStack Virtual に軍配が上がります。
開発のしやすさと機能のトレードオフが大きいため、作りたい「MetaCSV」の方向性によって選ぶべきエンジンが変わります。

1. Glide Data Grid vs TanStack Table 比較表


比較項目	Glide Data Grid (Canvas描画)	TanStack Table + Virtual (DOM描画)
描画方式	1枚の <canvas> に直接文字を描画	見えている行だけ <div> を生成
パフォーマンス	異次元の速さ（数百万行・数千列でも余裕）	十分速い（10万行程度なら60fpsで動作）
スプレッドシート機能	標準装備（矩形範囲選択、ドラッグフィル、Excelとのコピペ、列幅変更）	自前実装が必要（基本は表示とソート・フィルタのみ）
UIのカスタマイズ性	低い（CSSが使えず、Canvasの描画APIで座標計算して描く必要がある）	非常に高い（ReactコンポーネントやTailwind CSSをそのまま使える）
VS Code テーマ対応	テーマ変数（CSS変数）をJSで読み取って色オブジェクトに変換する必要がある	CSS変数（--vscode-...）をそのまま指定できる


2. どちらを選ぶべきか？（判断基準）


Glide Data Grid を選ぶべきケース

• 「10万行以上の巨大CSVを、Excel感覚でガシガシ編集したい」場合
• セルのドラッグ範囲選択、複数セルの一括コピー＆ペースト、キーボードの矢印キー移動などを最初から完璧に動かしたい場合（これらを自前で実装すると非常に大変です）。
• 見た目は標準的なスプレッドシート風で問題なく、メタデータ（JSONC）での制御は「列幅・表示/非表示・読み取り専用・ドロップダウン選択肢・文字色/背景色」程度で十分な場合。

TanStack Table + TanStack Virtual を選ぶべきケース

• 「メタデータ（JSONC）に応じて、セル内にリッチな独自UIを埋め込みたい」場合
• たとえば「特定の列にバッジやプログレスバーを表示する」「エラーがあるセルにツールチップを出す」「VS Code の UI デザインに完全に溶け込ませる」といった、Web（HTML/CSS）ならではの表現力を重視する場合。

3. 私のおすすめ（結論）

今回のテーマである 「メタデータを見て表示や列幅を制御する、決定版のCSVエディタ」 を個人で効率よく作り上げるなら、まずは Glide Data Grid を採用するのがおすすめです。
理由は、CSVエディタとしてユーザーが当たり前のように期待する「Excel的な操作感（範囲選択・コピペ・列幅ドラッグ・キーボード操作）」と「10万行の快適さ」が最初から完成しているからです。UIの作り込みに時間を奪われず、肝心な「JSONC メタデータとの連携ロジック」や「3環境（Web / Tauri / VS Code）の統合」に開発リソースを集中できます。

Glide Data Grid もCSS使えなくても見た目まともにする方法は一応あるの？

はい、Glide Data Grid は CSS が使えなくても、専用の theme プロパティとカスタム描画（drawCell）を使うことで、VS Code やモダンなアプリに完全に馴染む美しい見た目にできます。
むしろ、デフォルトの見た目が素っ気ないだけで、設定を少し整えるだけで一気にプロ仕様のスプレッドシートのような見た目になります。具体的な方法は大きく分けて3つあります。

1. theme オブジェクトで配色・フォントを一括指定する（基本）

Glide Data Grid には、背景色・文字色・罫線・選択範囲の色などを細かく指定できる theme プロパティがあります。ここにカラーコードやフォントを渡すだけで、全体の雰囲気をガラッと変えられます。
tsx
import { DataEditor, Theme } from "@glideapps/glide-data-grid";

// モダンなダークテーマ（VS Code風）の例
const customTheme: Partial<Theme> = {
  accentColor: "#007acc",          // 選択枠のアクセントカラー
  accentLight: "rgba(0, 122, 204, 0.2)", // 範囲選択時の半透明背景
  textDark: "#cccccc",             // 通常セルの文字色
  textMedium: "#999999",           // サブテキストの色
  textLight: "#666666",            // 薄い文字色
  bgCell: "#1e1e1e",               // セルの背景色
  bgCellMedium: "#252526",         // 偶数行や別領域の背景色
  bgHeader: "#2d2d2d",             // ヘッダーの背景色
  bgHeaderHasFocus: "#383838",     // 選択中列のヘッダー背景色
  bgHeaderHovered: "#333333",      // ホバー時のヘッダー背景色
  borderColor: "#3c3c3c",          // 罫線の色
  fontFamily: "'Segoe UI', 'Meiryo', sans-serif", // フォント指定
  baseFontStyle: "13px",           // 基本フォントサイズ
  headerFontStyle: "600 13px",     // ヘッダーのフォントスタイル
};

// コンポーネントに渡すだけ
<DataEditor theme={customTheme} ... />
コードは注意してご使用ください。

VS Code のテーマ色に自動追従させる裏ワザ

VS Code の Webview 上では、getComputedStyle(document.body).getPropertyValue("--vscode-editor-background") のように JS から VS Code の CSS 変数の値（カラーコード）を取得できます。これを customTheme に流し込めば、ユーザーがどんな VS Code テーマ（Monokai、Solarized、ライト/ダークなど）を使っていても完全に一体化します。

2. 列・セル単位の themeOverride で色分けする（メタデータ連携に最適）

全体のテーマだけでなく、「特定の列だけ背景色を変える」「読み取り専用の列を少しグレーにする」といった表現も、getCellContent が返すセルオブジェクトに themeOverride を付けるだけで CSS なしで簡単に実現できます。
tsx
// メタデータで readonly: true になっている列の見た目を自動で変える例
return {
  kind: GridCellKind.Text,
  data: cellValue,
  displayData: cellValue,
  allowOverlay: !colMeta.readonly,
  themeOverride: colMeta.readonly
    ? { bgCell: "#252526", textDark: "#888888" } // 読み取り専用は少し暗くする
    : undefined,
};
コードは注意してご使用ください。

3. drawCell コールバックでバッジやタグを描く（応用）

もし「status 列の done という文字を角丸の緑色バッジにしたい」といった凝った装飾をしたい場合は、drawCell というフックを使います。HTML の <span> は使えませんが、Canvas の 2D API で「角丸の四角形を描いて、その上に文字を描く」といった処理を数行書くだけで、非常に綺麗なラベルやプログレスバーを描画できます。
また、公式の拡張パッケージである @glideapps/glide-data-grid-cells を入れれば、最初から以下のようなリッチなセルUIがそのまま使えます。
• ドロップダウン選択（Enum）
• タグ・マルチセレクト（色付きピルバッジ）
• 日付ピッカー、星評価、スパークライン（ミニ折れ線グラフ）

結論

Glide Data Grid は「CSSが書けない＝見た目がダサくなる」わけではなく、「CSSの代わりに JS のオブジェクト（theme）でデザインを定義する」という設計になっています。
• 全体の雰囲気・VS Code 馴染み: theme に VS Code の CSS 変数を読み込んで渡すだけで完璧になる。
• メタデータによる見た目制御: themeOverride と公式の glide-data-grid-cells（ドロップダウンやタグなど）を組み合わせれば、CSS なしでも実用上まったく困らないレベルまで綺麗に仕上げられます。

その通りです。10年スパンで長く使われるツールを目指すなら、最初から10万行を想定してアーキテクチャを組んでおくのが大正解です。 10万行規模の長期運用を前提に設計しておきましょう。
後から「行数が多くて重くなったから描画エンジンを総入れ替えしよう」となると、UIからデータ管理までほぼ作り直しになってしまいます。最初から10万行を余裕でさばける土台を作っておけば、普段使いの小さなCSVから業務用の巨大CSVまで、10年後もストレスなく現役で使い続けられます。

1. 10年後も戦える「10万行前提」の設計方針

1. 描画エンジンは Glide Data Grid 一択
	• Canvas 描画なので、10万行でも100万行でも描画の重さは変わりません。将来ブラウザやマシンスペックが進化しても、この設計は陳腐化しません。
2. データ構造は「配列の配列」または「オフセットインデックス」で持つ
	• [{ id: 1, name: "..." }, ...] のようなオブジェクト配列ではなく、単純な2次元配列 string[][]（またはバイナリの行位置インデックス）で保持します。これだけでメモリ消費量を半分以下に抑えられ、10万行でもブラウザのメモリ制限に引っかかりません。
3. 重たい処理は最初から Web Worker に分離する
	• CSVのパース、10万行の全文検索・フィルタリング、ソート処理は最初から別スレッド（Web Worker）に逃がしておきます。これにより、検索文字を打ち込んでいる最中でもUIの操作感が一切損なわれません。

2. 今後のメンテナンス性を高めるポイント（10年見据えるなら）

• メタデータ（JSONC）の仕様をシンプルかつ疎結合に保つ
	• 特定のライブラリ（Glide Data Grid など）に依存したプロパティ名ではなく、width、visible、label、wrap といった普遍的な意味の名前で JSONC を設計しておきます。
	• そうすれば、仮に10年後に別の新しいUI技術に乗り換えたくなっても、ユーザーの .meta.jsonc ファイルは一切書き換えずにそのまま資産として引き継げます。
• CSV本体への書き込みは「差分更新」または「ストリーミング出力」を意識
	• 10万行を編集して保存する際も、UIをブロックせずバックグラウンドで文字列化して保存する仕組みにしておけば安心です。

Antigravityさんに合わせて検討してもらうべき7つの論点

1. 列の紐づけ方式（Column ID vs 列インデックス）
	• CSVにヘッダー行がある場合（列名 "email" で紐づけ）と、ヘッダー行がない場合（列番号 0, 1, 2... で紐づけ）の両方をどう扱うか。
	• 列の順番を入れ替えたり、途中に新しい列を追加したりしたときに、メタデータ（列幅など）がズレない仕組みをどうするか。
2. CSVの「方言（Dialects）」の自動判定と保存時の維持
	• 文字コード: UTF-8（BOMあり/なし）、Shift-JIS（CP932）の自動判定と、保存時に元の文字コードを壊さない仕組み。
	• 改行コード・区切り文字: CRLF / LF、カンマ（,） / タブ（TSV）の自動判定と維持。
3. 保存タイミングと「dirty（未保存）状態」の管理
	• CSV本体: 勝手に上書きされると危険なため、明示的な保存（Ctrl+S / Cmd+S）やUndo/Redo履歴をどう持つか。
	• メタデータ（.meta.jsonc）: 列幅をドラッグして変えた瞬間に自動保存（デバウンス処理付き）するのか、それとも手動保存にするのか。また、まだメタデータが存在しない状態で開いたとき、いつファイルを生成するか（列幅を初めて変えた瞬間など）。
4. メタデータファイルの探索ルールと命名規則
	• data.csv に対して data.csv.meta.jsonc を基本としつつ、フォルダ全体の共通ルール（例: .metacsv.jsonc）やグロブパターン（logs_*.csv には同じメタデータを適用する等）をサポートするか。
5. 10万行編集時の「Undo / Redo（元に戻す）」設計
	• 10万行の配列全体をスナップショット保存するとメモリがパンクするため、コマンドパターン（変更したセルの座標・変更前・変更後の差分だけを記録する方式）を採用する設計。
6. VS Code 拡張機能特有の「ファイルサイズ制限」の回避策
	• VS Code 標準の CustomTextEditorProvider は巨大ファイル（数万〜10万行）で制限に引っかかることがあるため、拡張機能側（Node.js）でファイルを読み込み、Webview とは必要な表示範囲（チャンク）だけをメッセージ通信でやり取りする設計にするか。
7. モノレポのディレクトリ構成と通信インターフェース（Adapter）の定義
	• packages/core（CSVパース・メタデータ管理・型定義）
	• packages/ui（React + Glide Data Grid）
	• apps/web / apps/desktop（Tauri） / apps/vscode
	• これらを繋ぐ FileSystemAdapter インターフェースの具体的なメソッド定義。
